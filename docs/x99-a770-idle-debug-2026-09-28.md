# X99 + Intel Arc A770 LE idle-power investigation — 2026-09-28

This note captures a headless Ubuntu / Intel Xe driver investigation on an Intel Arc A770 16 GB Limited Edition installed in an older X99 / Xeon system.

## Final observed runtime-PM state

With GPU workloads stopped and sleep-aware monitoring in place:

```text
power/control: auto
runtime_status: suspended
runtime_usage: 0
power_state: D3hot
autosuspend_delay_ms: 1000
d3cold_allowed: 1
```

The GPU can automatically wake to D0 when needed and return to D3hot afterwards.

## Wake source 1: DRM connector polling

ftrace identified a kernel display-polling wake path approximately matching the periodic wakeups seen on the headless server:

```text
output_poll_execute
  -> drm_helper_probe_detect_ctx
  -> intel_dp_detect
  -> intel_digital_port_connected
  -> xe_display_rpm_get
  -> xe_pm_runtime_resume_and_get
  -> rpm_resume
```

Temporarily disabling DRM KMS polling:

```bash
echo N | sudo tee /sys/module/drm_kms_helper/parameters/poll
```

reduced GPU active residency from roughly 11–12 seconds per minute to roughly 4 seconds per minute.

This setting is temporary across reboot unless made persistent. On systems where a display may later be attached, disabling connector polling can affect automatic hotplug detection.

## Wake source 2: reading Xe act_freq while suspended

A custom Python idle-monitor process was caught waking the GPU by reading the Xe active-frequency sysfs file:

```text
python
  -> sysfs read
  -> act_freq_show
  -> xe_pm_runtime_get
  -> __pm_runtime_resume
  -> rpm_resume
```

The monitor originally did this unconditionally:

```python
gpu_status = GPU_RUNTIME_STATUS.read_text().strip()
driver = GPU_DRIVER.resolve().name
gpu_frequency_path = GPU_ACTIVE_XE if driver == "xe" else GPU_ACTIVE_I915
gpu_frequency = int(gpu_frequency_path.read_text().strip())
```

It was changed so that frequency is read only if the GPU is already active:

```python
gpu_status = GPU_RUNTIME_STATUS.read_text().strip()
if gpu_status == "suspended":
    state["gpu_active_samples"] = 0
else:
    driver = GPU_DRIVER.resolve().name
    gpu_frequency_path = GPU_ACTIVE_XE if driver == "xe" else GPU_ACTIVE_I915
    gpu_frequency = int(gpu_frequency_path.read_text().strip())
    ...
```

After this change, observed active residency dropped to roughly 1–2 seconds per minute.

## Wake blocker: ComfyUI keeping the render node open

After a reboot, the GPU remained in D0 with:

```text
runtime_status: active
runtime_usage: 2
```

`lsof` identified ComfyUI:

```text
python ... /home/aiadmin/ai/apps/ComfyUI/main.py ...
  /dev/dri/renderD128 FD 3
  /dev/dri/renderD128 FD 6
```

The two open render-node file descriptors matched `runtime_usage=2`.

Stopping ComfyUI returned the GPU to:

```text
runtime_status: suspended
runtime_usage: 0
power_state: D3hot
```

For a headless low-idle-power server, ComfyUI should therefore be started only when needed rather than kept permanently running if runtime suspend matters.

## Energy-counter measurement

A cumulative Xe hwmon energy counter was sampled across long idle intervals.

Observed results:

```text
30 s interval:
energy delta: 1,087,265,502 uJ
calculated average: 36.205 W
runtime active delta: 0 ms
runtime suspended delta: 30,030 ms

120 s interval:
energy delta: 4,197,741,455 uJ
calculated average: 34.952 W
runtime active delta: 2,552 ms
runtime suspended delta: 117,549 ms
```

The energy delta scaled with elapsed time, including an interval where runtime active time did not increase at all. On this system, the package energy counter therefore continued to indicate about 35 W even while runtime PM reported D3hot for essentially the whole interval.

Important implication:

> Runtime `D3hot` is evidence that runtime PM is functioning, but it does not by itself prove that the board/package has reached a very low physical idle wattage.

## PCIe / ASPM findings

Kernel boot log:

```text
ACPI FADT declares the system doesn't support PCIe ASPM, so disable it
FADT indicates ASPM is unsupported, using BIOS configuration
r8169 ... can't disable ASPM; OS doesn't have ASPM control
```

Kernel configuration:

```text
CONFIG_PCIEASPM=y
CONFIG_PCIEASPM_DEFAULT=y
```

Runtime policy remained:

```text
[default] performance powersave powersupersave
```

Attempting to write `powersupersave` returned `Operation not permitted`, consistent with the firmware/ACPI decision that the OS does not control ASPM.

## Working interpretation

The software wakeups were real and worth fixing, but after those were removed the A770 package energy counter still stayed near 35 W.

The remaining limitation on this specific machine is consistent with the older platform/firmware not exposing a complete L1.1/L1.2 path from the CPU root port through the A770 PCIe topology.

The X99 root port exposes ordinary L1 but no visible L1SS capability. The A770 internal bridge advertises L1.1/L1.2 but they are disabled. The firmware FADT also prevents Linux from taking ASPM policy control.

This makes a platform/firmware PCIe power-management limitation the leading explanation for the remaining idle wattage.

## BIOS notes

The tested BIOS had a global PCIe ASPM setting configured to **L1 Only**.

That was enough to produce L1 on the upper link, but it did not enable L1.1/L1.2.

Potentially relevant firmware options on other boards include:

- Native ASPM
- PCI Express ASPM
- L1 Substates
- L1.1
- L1.2

A BIOS update can potentially change ACPI/FADT behavior or expose additional controls, but it cannot add physical L1SS support if the root-port hardware itself lacks that capability.

## Safety note

Do not treat `pcie_aspm=force` as a routine fix.

It can force ASPM on links the firmware did not declare safe. On old platforms and complex discrete-GPU topologies, that can lead to instability or devices disappearing from the PCIe bus.

## Practical configuration reached

For this machine:

1. Keep A770 `power/control=auto`.
2. Do not read Xe hwmon/frequency sensors while runtime-suspended.
3. Disable unnecessary GPU polling in monitoring agents.
4. On the headless server, disable DRM connector polling if the hotplug tradeoff is acceptable.
5. Do not keep ComfyUI running when it is not needed.
6. Treat D3hot and real power consumption as separate measurements.
7. Investigate firmware updates / a newer platform if reducing the remaining ~35 W is a priority.
